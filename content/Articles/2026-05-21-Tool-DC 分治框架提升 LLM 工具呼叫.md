# Tool-DC：分治框架解決 LLM 海量工具呼叫難題，7B 模型達 o3 水準

> [!info] 文章資訊

## 📝 重點摘要

來自 Wuhan University 與 University of Sydney 的研究團隊提出 **Tool-DC（Tool-Calling with Divide-and-Conquer）**，一個透過「嘗試-檢查-重試（Try-Check-Retry）」範式解決大型語言模型在**長上下文工具呼叫**場景下性能瓶頸的框架。現有 LLM 在面對大量候選工具時（如企業 API 目錄有數百個工具），往往因為長上下文中「工具雜訊」過多而出錯。Tool-DC 分為免訓練（TF）與訓練增強（TB）兩個版本：TF 版本無需微調，即插即用，在 BFCL 與 ACEBench 基準測試上平均提升高達 **+25.10%**；TB 版本讓 Qwen2.5-7B 達到與 OpenAI o3 及 Claude Haiku 4.5 相當甚至更佳的性能，大幅降低企業部署工具呼叫 AI Agent 的成本門檻。

## 📖 全文內容

### 工具呼叫：AI Agent 的關鍵能力瓶頸

在 AI Agent 大規模落地的 2026 年，「工具呼叫（Tool Calling）」已成為 LLM 最核心的實用能力之一。無論是企業 RPA、Copilot、多步驟任務自動化，Agent 都需要正確識別並呼叫合適的 API 工具。

但實際部署中，這個能力面臨一個被低估的挑戰：**現實環境的工具數量往往遠超訓練假設**。

訓練階段的 LLM 工具呼叫通常假設：「從 5-20 個候選工具中選一個」。但真實企業環境中，工具目錄可能包含：
- 數百個不同 API 端點
- 功能相似但參數不同的工具
- 版本迭代留下的舊工具
- 跨部門整合帶來的命名不一致

這造成「**長上下文工具呼叫（Long-context Tool Calling）**」問題：當所有工具描述都被放入上下文，LLM 面臨的 context length 可能超過 10 萬 tokens，大量無關工具形成嚴重「雜訊干擾」，導致模型選錯工具、參數填錯，整個 Agent 鏈路失敗。

### 分治思想：Tool-DC 的核心設計

Tool-DC 借鑒計算機科學中經典的「分治（Divide-and-Conquer）」演算法思想，把「在大量工具中找到正確工具」拆解成可管理的子問題：

**第一步：Divide（分割）**

不要把所有工具一次塞進 context，而是把工具目錄切成若干小批次（batch），每批只包含少量候選工具。這讓每次決策的工具雜訊大幅降低。

**第二步：Try（嘗試）**

對每個批次，讓 LLM 「嘗試」識別哪些工具可能與當前任務相關，並初步生成工具呼叫計劃。

**第三步：Check（檢查）**

透過一個輕量的「檢查機制（Checker）」評估嘗試的品質——這是 Tool-DC 的關鍵創新：利用 LLM 自身的**自我反思（self-reflection）**能力，判斷初步方案是否合理，識別潛在錯誤（如工具選錯、參數缺失、邏輯矛盾）。

**第四步：Retry（重試）**

如果 Checker 發現問題，觸發「重試（Retry）」——利用 Checker 的診斷反饋修正工具呼叫方案。這個「嘗試-檢查-重試」迴圈是 Tool-DC 名稱的由來。

**最後：Conquer（整合）**

把各批次的候選工具評估結果整合，得到全局最優的工具呼叫決策。

### 兩種版本的設計取捨

**Tool-DC (TF)——免訓練版本（Training-Free）**

TF 版本完全不需要微調現有模型，只需在推理階段應用 Try-Check-Retry 邏輯。這讓它可以「即插即用」到任何現有 LLM（GPT-4、Claude、Llama 等），作為 prompt engineering 層面的增強。

優點：靈活、無需訓練成本、可立即部署
侷限：依賴基礎模型的自我反思能力，小模型效果有限

**Tool-DC (TB)——訓練增強版本（Training-Based）**

TB 版本在免訓練框架基礎上，針對 Try-Check-Retry 模式進行監督微調（SFT）或強化學習（RL）訓練。論文選用 Qwen2.5-7B 作為基礎模型，訓練它更擅長：
- 識別自身工具呼叫中的潛在錯誤
- 透過 Checker 反饋有效修正
- 在工具雜訊環境中保持精準

優點：性能更強、推理效率高
侷限：需要訓練成本，模型更換需重新訓練

### 實驗結果

論文在 BFCL（Berkeley Function Calling Leaderboard）和 ACEBench 兩個工具呼叫基準測試上評估 Tool-DC：

**Tool-DC (TF) 結果**：
| 基準 | 基線 | Tool-DC (TF) | 提升 |
|------|------|-------------|------|
| BFCL | 各模型基線 | 平均 +25.10% | **顯著** |
| ACEBench | 各模型基線 | 平均 +25.10% | **顯著** |

**Tool-DC (TB) 結果**——Qwen2.5-7B 的表現：
- 達到或超越 OpenAI o3 的工具呼叫性能
- 達到或超越 Claude Haiku 4.5 的工具呼叫性能
- 在「高工具密度」場景（100+ 候選工具）下優勢更明顯

這個結果的意義是：企業不需要花費大量成本部署 o3 或 Claude Haiku 4.5 等閉源大模型，就能獲得同等的工具呼叫性能——只需要一個 7B 開源模型 + Tool-DC TB 框架。

## 💡 觀察與啟發

Tool-DC 的出現揭示了 AI Agent 落地的一個關鍵「最後一哩路」問題：**工具呼叫性能是否在現實複雜度下依然可靠**。學術 benchmark 通常只有 10-20 個工具，而真實企業 API 目錄可能有 200-500 個端點——這個差距導致很多在 demo 上完美運作的 Agent 在生產環境中頻繁出錯。

從工程實踐角度，Tool-DC 的分治思想非常務實。它不需要改變現有 LLM 的架構或重新訓練大模型，只需在推理時加入分治邏輯。對於已經使用 LLM 的企業，TF 版本的「即插即用」特性意味著幾乎零遷移成本就能改善 Agent 在複雜工具環境中的準確率。

7B 模型達到 o3 水準的工具呼叫能力，這對台灣與東亞企業有特別的戰略意義——許多企業因為資料主權、成本、延遲等因素，偏好在地部署（on-premise）小型模型而非呼叫雲端大模型。Tool-DC TB 讓在地部署的中小型開源模型在工具呼叫任務上具備與頂級閉源模型媲美的能力，為企業 AI Agent 落地提供了更具成本效益的路徑。
